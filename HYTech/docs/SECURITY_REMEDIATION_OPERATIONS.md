# Security remediation operations

This runbook covers actions that cannot be safely completed by repository code.
Perform them first in staging and retain screenshots, command output, timestamps,
the acting administrator, and the reviewed project ID as audit evidence.

## Exposed-account incident response

1. Disable or delete the formerly published admin, trainer, and student accounts.
2. Revoke refresh tokens for every retained account and assign unique passwords.
3. Search Firebase Authentication, Firestore, Cloud Functions, and Cloud Audit
   Logs for those UIDs from the first publication date through the revocation.
4. Review role, status, enrollment, grade, progress, certificate, rule, and user
   changes attributable to them.
5. Record whether notification to the DPO or affected people is required.

Deleting the credentials from current documentation does not invalidate copies
in repository history. Rotation/revocation is mandatory.

## App Check

1. Create separate reCAPTCHA/App Check web registrations for staging and production.
2. Set `VITE_RECAPTCHA_SITE_KEY` in the matching GitHub environments.
3. Confirm no production `VITE_APPCHECK_DEBUG_TOKEN` exists.
4. Observe App Check metrics in staging, then enforce Cloud Firestore, Storage,
   and Functions.
5. Verify a legitimate request succeeds and the same request without attestation
   is rejected.

All callable Functions in this repository declare `enforceAppCheck: true`.

For a local staging build, append the key to the existing environment file
rather than copying the example over it:

```powershell
Add-Content ".env.staging.local" "VITE_RECAPTCHA_SITE_KEY=<staging-site-key>"
```

`Copy-Item .env.staging.example .env.staging.local` overwrites a populated file
with blanks.

## Staging deployment prerequisites

- `firebase.json` declares Hosting, Firestore, Storage, and Functions, so
  `firebase deploy` targets all four. Confirm `hytech-lms-staging` is on the
  Blaze plan before deploying; Functions deployment fails otherwise.
- `npm run deploy:staging` deploys Hosting only and is not sufficient for a
  security release.
- Commit and push before deploying to staging. A local deploy publishes the
  working tree, so an uncommitted staging build is not the code that a
  production release will later ship.

## Test expectations

- `npm run test:unit` — 8 CSV hardening tests (6 generated by `it.each`, plus 2).
- `npm run test:rules` — 10 Firestore and Storage authorization tests
  (both suites live in `tests/rules/firestore.rules.test.js`).
- `npm run security:secrets` — scans the whole repository, including
  documentation outside `HYTech/`.
- The `playwright` job in `qa.yml` serves a staging-configured build from a
  local preview server. It does not exercise the deployed staging site; run
  that separately with `E2E_BASE_URL=https://hytech-lms-staging.web.app`.

## Academic-data migration

1. Export/backup Firestore and Storage.
2. Run `npm run audit:academic` with staging credentials.
3. Review inline answer keys, unverified progress, and legacy certificate references.
4. Run `npm run migrate:academic` only after review.
5. Recalculate progress through the application/Function for each active enrollment.
6. Reissue or revoke legacy certificates through an approved academic workflow.
7. Repeat the dry-run audit until no inline answer key remains.

The migration marks legacy progress as unverified; it does not silently certify it.

Both scripts read `FIREBASE_SERVICE_ACCOUNT_JSON` and `GOOGLE_CLOUD_PROJECT`,
and emit the report as JSON on stdout. Use `npm run --silent` when capturing to
a file, otherwise npm's banner lines make the saved report unparseable:

```powershell
npm run --silent audit:academic | Tee-Object -FilePath "C:\secure\staging-academic-audit.json"
```

Confirm `projectId` and `mode` in the saved report before applying anything.

## Production release

1. Configure the GitHub `production` environment with required reviewers.
2. Add the production App Check variable and existing Firebase deployment credential.
3. Prefer Workload Identity Federation and a least-privileged service account;
   remove the long-lived `FIREBASE_TOKEN` after WIF succeeds.
4. Require the QA workflow to finish successfully. `workflow_dispatch` on
   `deploy.yml` is a rollback path that skips QA; it is restricted to `main`
   and still requires production environment approval.
5. Approve the production environment deployment.
6. Confirm the deployed commit and run post-deploy enrollment, isolation, grading,
   progress, certificate, Storage, CSV, CSP, and App Check smoke tests.

## Backup and recovery

- Define and approve RPO/RTO.
- Schedule Firestore exports and Storage replication/backups to an isolated target.
- Restore into a nonproduction project at least quarterly.
- Verify Auth dependencies, indexes, rules, files, progress, certificates, and logs.
- Exercise Hosting rollback and redeployment of rules/Functions from a known-good release.

## Governance sign-offs

Named owners must approve and retain evidence for:

- privacy notice, lawful basis, data-subject rights, retention, and legal hold;
- DPO/PIA/registration/reporting requirements;
- Firebase/AI/other processor agreements;
- minor/guardian safeguards where applicable;
- grading, attendance, competency, reassessment, overrides, and appeals;
- certificate issuance, correction, retention, and revocation;
- TESDA/TVET applicability;
- accessibility verification;
- monitoring/on-call ownership and staff/vendor offboarding.
